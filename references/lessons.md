# 清华自动预约 · 开发迭代可复用经验清单（体育场馆 + 活动室 合并版）

> 用途：合并合作伙伴 auto-reserve 功能 / 优化对方 skill 设计时参考。已合并去重，按主题归类；标 🅢=体育场馆、🅐=活动室、🅢🅐=两者通用。

## 一、认证与会话

1. **🅢 SSO 要走「带 service 的登录地址」**：先 `GET /cas/address?redirectUrl=<业务首页>` 拿带 service 的统一登录地址，再 goto；登录后 CAS 自动回跳业务站换 token，用户只登录一次。→ 适用于一切「CAS/统一认证 + 业务 token」。

2. **🅢 先查浏览器已有会话，命中免登录**：登录前用无头浏览器打开业务站读 `localStorage.token`，命中直接复用。→ 避免重复登录。

3. **🅢🅐 凭证双/多持久化 + 进程内多 token 要服务端校验**：
   - 体育：同时保存 token + 完整 Cookie，纯 HTTP 命令可直连（避开沙箱）。
   - 活动室：进程内存里有多份旧 token，取「第一个」会拿到已吊销的——**用只读接口逐个校验到有效为止**，有效缓存复用，失效再扫。
   - 价值：凭证都有「过期 + 会话轮换吊销」双重失效，别只按 exp 判断。

4. **🅢 浏览器 profile 互斥锁**：`.lock` 文件 + PID 存活检测，抢锁失败排队等。→ 任何持久化浏览器 profile 的自动化都适用。

5. **🅢🅐 内存字符串解码陷阱**：从 V8/Chromium 内存取 token 时按 **ASCII/Latin-1 单字节**搜（别用 UTF-16，会被空字节夹断）。

## 二、接口签名与加解密（🅢）

6. **每个请求都要签名**：`appId + timeStamp(ms) + nonce(32位随机) + sign=md5("appId=…&nonce=…&timeStamp=…&key=…")`；`x-api-version: 2.0.0` 只加在 `/api/*`。→ 正元智慧系通用签名范式。

7. **响应可能是 AES 加密字符串**：响应体是字符串而非 JSON 时，用 AES-256-CBC（key=32字节、IV=全0、Iso10126，去末尾 padding）解密后再 parse。→ 正元智慧系通病。

## 三、API 逆向与调试（🅢🅐）

8. **抓真实报文，而非只读源码**：用 `page.route('**/addReserve**', …)` 拦截（glob 要带 `**` 匹配 query 串）；字段结构以 F12 实测报文为准。→ 合并他人代码前先抓包校准。

9. **接口文档必须区分「实测 / 逆向未实测 / 不可用」**：凡是只逆向、没真正调通的（如早期 `cancelReserve`、`reserve-api` 因验证码 token 单次使用而不可用）明确标注，不向用户承诺。

10. **「提交」可能是多步，且资源 id 在响应头而非 body**：活动室=「创建 ticket（Location 头返回 id）→ 再 apply（204 空 body）」。→ 别假设单步提交，响应头常藏关键 id。

11. **空响应体（204）别当 JSON 解析失败**：HTTP 封装对空 body 返回「状态+空对象」，204 视为成功。

## 四、数据结构与字段语义（最重要，踩坑最多）

12. **🅢 同名多场馆：模糊匹配返回「多个」而非「第一个」**：先精确后包含，返回数组；查时段时合并并各自标注场景名。

13. **🅢🅐 字段语义不可想当然，要实测**：
    - 体育：`paidAmount` 是「应付金额」非「已支付」；`reserveRecord` 是 POST 不是 GET；分页是 `pageNum/pageSize`；`resvMember` 是纯 ID 字符串数组。
    - 活动室：`participantCount` 是字符串、`start/end` 是 epoch 毫秒（北京+8 转 UTC）、`activityTarget` 全校唯一值、`records` 的 `roomId` 是 UUID 字符串。
    - 价值：合并他人代码时字段名/类型/方法必须实测，不能按直觉。

14. **🅢🅐 枚举/下拉要「滚动到底」枚举全 + 建映射表**：活动室活动类型下拉可滚动、共 7 项（别凭首屏 5 项写死）；体育状态枚举建映射（`resvStatus`/`orderStatus`/`status`）。

15. **🅢🅐 位置/对象级规则做成数据表**：活动室 `LOCATION_RULES`（开放时段/最短提前天数/单次上限）；体育场次规则同理。→ 规则随对象变化时只改数据表。

16. **🅢🅐 时间：存储按接口约定、展示统一北京时间；周几用 `date.weekday()` 而非偏移**。

## 五、预约/申请核心逻辑

17. **🅢🅐 「先笼统 → 按可约定精确」的渐进式收集**：先问「哪天/上午下午/时长/人数」，用可约接口反查精确时段让用户挑。→ 降低输入成本 + 自动避开不可约。

18. **🅢🅐 提交前校验 + 失败自动回滚**：
    - 活动室：提交前校验「时段冲突、每日1次、人数≤容量、时长≤2h」；创建成功但提交失败→自动删草稿。
    - 体育：预约前查「未生效（未来）订单」软提醒，失败让用户先支付/取消再重试。

19. **🅢🅐 优先「最匹配」、灰色/备选方案放最后**：先按实际需求推最匹配（2人→2人房）；只有最匹配不可约时才给「更大对象 + 换场」备选，且灰色路径需用户显式确认、有边界。**如实申报人数，不得虚报填高**。

20. **🅐 两步提交 + 响应头取 id**：见 #10；提交前预校验命中要给出「时段被占 / 该日期已约过」等明确原因。

21. **🅢 验证码 token 单次使用 → 纯 API 预约不可行**：滑块 token 由前端校验后立即消耗，拿不出来；如实标注「API 提交 + 手动传 token 不可行」，别承诺纯 API 预约。

22. **🅢 动态表单可能是「空表单」**：简单场景表单 `fields:[]`，所以 `variables/chooseCandidates` 传 `{}`；判断「能不能纯 API 提交」前先看表单复杂度。

## 六、规则与校验

23. **🅢🅐 区分「接口硬约束」vs「使用/审核规范（软约束）」**：接口允许多时段/超2h（不硬拦），但「单次≤2h、每日1次」是审批规范——硬约束脚本拒绝，软约束显式提示「可能审不过」。

24. **🅢🅐 规则两两核对，防矛盾**：曾发现「时长示例写『半天』 vs ≤2h」「『分次』 vs 每日1次」「默认不变 vs 人数变少要换房」三处矛盾。→ 规则集写成后要交叉核对，尤其「默认/兜底」类规则最易被架空。

25. **🅢 取消有「提前 24 小时」硬限制**：`cancelBeforeStartTime=1440` 分钟，不足返回 401000103；取消前先算时间差，按实际情况告知能否取消。

## 七、错误处理与状态管理

26. **🅢🅐 失败给「具体原因」而非笼统状态码**：透出 409/412 的响应体 `{code,message}`；预校验命中给明确文案。

27. **🅐 「撤销/删除/草稿」三种状态分清楚**：已提交→撤销会回到草稿箱；`revoke` 对草稿返回 412；删草稿用 `remove`；「撤销=自动撤销+删草稿」做成固定步骤。

28. **🅢🅐 输入显式校验，别静默传坏值**：人数必须数字且≤容量、时长≤2h；否则拒绝并给原因。

## 八、并发、限流与性能（🅢）

29. **限流是「单并发」而非「限频」**：并发 2 个就 1610001；时段查询必须串行，别用 Promise.all。→ 限流类型要实测判定。

30. **「当天」查询又慢又大 → 默认跳过**：默认「从明天起查」，`--date` 显式查当天。→ 查询默认范围避开慢路径。

31. **场景名单/上下文缓存**：名单缓存 10 分钟、上下文缓存到本地文件，省重复全量调用。

32. **输出按「日期+时段」聚合，别逐片罗列**：把「羽1…羽14」聚合成「14 片」。→ 列表按用户决策粒度聚合。

## 九、配置管理与隐私（🅢🅐）

33. **个性化配置放用户目录，不写进可分享的 skill**：`config org` 存 `~/.thu-sports-venue/`，`apply` 自动复用；示例一律占位符。

34. **示例/文档/代码不落真实个人信息**：姓名/学号/手机/邮箱一律占位符，发现泄漏立即全库 grep 清理 + 清空本地 config。

35. **多脚本共享同一配置要对齐路径/格式**：`wechat-room-api.py` 与 `wechat-room.py` 共用同一 config 文件、key 一致，避免「存了读不到」。

## 十、沟通与交互 UX（🅢🅐）

36. **对用户只讲自然语言，不暴露内部命令/脚本/API/流程**：用户面向的「告知/提问」禁止出现 `list/apply/mine/--yes/records/jwt` 等；内部命令只存在于 agent 指令。

37. **交互组件按场景选型**：`question` 提问框用于「收集表单字段」（活动室 + 图书馆研讨间）；自然问答（体育推荐、自习座位）不用。别机械套用。

38. **每问一项给「比表格更丰富」的信息**：列全部选项、给格式/示例，不漏表格本有的内容。

39. **字段依赖顺序要显式声明**：主题→类型→内容（类型按主题定、内容围绕主题）；人数→选房。写成「必须先问 X，再问 Y」。

40. **AI 代写文案「正式但不 AI 腔」**：完整陈述句、正式动词，但不用 ①②③ 分点、不用「议程/环节/产出/技术路线」空词、也不过分口语。

41. **开场告知能力 + 每步告知下一步 + 提交后告知后续**：三处「告知」固定下来，让用户始终知道能干什么、接下来干什么。

42. **多选项对比要「说全差异」**：场馆对比时片数/场地质量/位置/新旧/价格缺一不可，只讲「交通方便/较新」不合格。

43. **提示按实际情况，不盲目承诺**：取消按 24h/待支付/已支付分别说；不满足就如实说。

## 十一、脚本健壮性（🅢🅐）

44. **同义词/近义词显式归组，避免漏配**：把「会议/研讨/讨论」统一到同一组关键词（都含「研讨」），否则「小组讨论」漏「小型研讨室」。

45. **同一能力跨命令参数面要对齐**：`recommend` 和 `avail` 都支持 `--purpose`，别一个支持一个只认 `--type`。

46. **npm 脚本白名单用对象格式**：`allowScripts: {"playwright": true}`（对象），写数组会解析成错键；安装前移除 `npm_config_allow_scripts`。

47. **浏览器优先系统 Chrome/Edge，不强制下载 Chromium**：省下载、避沙箱问题。

## 十二、流程标准化（🅢🅐）

48. **固定流程 + 固定提问顺序**：活动室「确认需求→查房→查可约(+每日1次提示)→选房→收集(主题先)→汇总→提交→提交后告知」；体育同理。→ 可复现、可交接、可回归。

49. **数据可能「临时下架」，用软提示而非写死**：某位置/场次临时从接口消失时，保留完整数据 + 加「可能临时下架（不必惊慌），以实时为准」，别删数据或写「已停用」。

50. **能力概览「开场即告知」**：进入分支先一句话告知可做什么（推荐/查时段/预约/抽签/查看取消/撤销）。

51. **🅢🅐 数字与选项编号要区分**（十 沟通）：问「人数/时长/几天」等数字字段时让用户直接说数字，不要放进①②③选项；若用户回数字且旁有选项列表，先澄清是数字还是选项编号，别擅自当选项。（数字答案被当成选项编号是收集信息时最易踩的坑。）
52. **🅢🅐 排查/调试时也别暴露命令/参数/函数名**（十 沟通）：即使内部在查命令/看参数/看函数/看匹配逻辑（出 bug 排查时也一样），也不要说「我跑一下 X」「确认 X 参数」「看 normName 匹配」——用户只需自然语言结果。仅约束「正常流程不暴露」会漏掉「排查时」，泄漏常发生在 agent 排查登录/参数/匹配逻辑时，且**连函数名（如 normName）、内部实现细节都不该说**。
53. **🅢🅐 时间可行性要先校验再收集**（五 预约核心）：用户提出时间范围后，先对照规则（如双人舱≤2.5h、开放时间、提前天数）确认可行，再收集成员学号/提交；别等最后提交预演才因超限返工。
54. **🅢🅐 提示按真实规则，别编造**（六 规则校验）：给「能否取消/每日限制」等信息按实际规则说（如研讨间「每天最多1个有效预约、取消后可再约」，不是「取消后当天不能再约」）；把「每日限取消1次」错误套到研讨间会误导。
55. **🅢🅐 查询 0 结果提示「过滤太严」**（十一 脚本健壮性）：avail/recommend 查不到时给「通常容量/类型/用途/位置过滤太严，可放宽/去过滤/用 `list` 看全部」提示，避免 agent 误判「参数名错了」反复重试。
56. **🅢🅐 系统自动计入本人 + 成员去重**（五 预约核心）：预约系统自动把当前登录账号算作一位成员；告知用户「成员只需填其它同学」，脚本对成员证号去重（==本人则跳过），避免「本人误填」导致人数多算、提交被拒。
57. **🅢🅐 行为/口径改变后，同步所有交叉引用文档**：如 `question` 提问框从「仅活动室」扩展到「活动室+研讨间」后，需同步 SKILL / lessons / DEVELOPER 的口径，否则会残留「只用于活动室填表」这类过时矛盾。→ 每改一处行为，回头 grep 交叉引用（lessons 编号、DEVELOPER 逐条核对、README 用户版）一并更新。
58. **房间/对象名匹配要支持简称/子串**（十一 健壮性）：预约/查询时房间名若带备注（如「法F5-研讨舱1（4人间）」），用户/agent 只给简称「法F5-研讨舱1」也要能匹配——脚本「先精确再子串（双向包含）」，别只 `normName(a) === normName(b)` 精确相等，否则会「未找到房间」。
59. **🅢🅐 静态凭证要加密 + 留存时长要合理**（九 配置与隐私）：存本机的 token/会话/JWT 应**加密**（AES-GCM，密钥按机器+用户派生，防拷文件/备份/云同步），并**设定留存上限**（此处与后端 jwt 有效期对齐、约 7 天；若评审允许更短可再缩短留存时长），到期自动按未登录处理；可显著收窄「文件被偷后长期冒用」的面。→ 注意只保护「静止」，不覆盖「内存读取/使用中明文」；留存时长是「安全 vs 免登录便利」的权衡，需与评审确认。
60. **🅢🅐 如实申报，不作弊/不教唆**（六 规则校验）：参与人数、材料等按实际填写，**不要**「填高提高通过率」这种不诚实做法——安全/合规扫描会判定为不诚实提交，且本质是失信。→ 容量不符时优先换更匹配的资源，而非虚报。

61. **🅢 用户给了具体日期就 `--date` 单日查，别用 `--days` 扫多天**（十二 流程标准化）：用户说「今天/明天/大后天/某月某日」这种**具体日期**时，直接 `slots --date <该日期>` 只查那一天（最快、结果最聚焦），不要用 `--days N` 扫未来多天——扫多天会把无关日期的场次混进来干扰判断，还可能误触限流；`--days` 只在用户要「未来几天」的笼统范围时用。→ 「具体日期 vs 范围」要先分清再选参数。

62. **🅢🅐 沙箱/权限：先预检、先提权，别先跑再补**（十一 脚本健壮性）：涉及读写本机 `~/.thu-*`（登录态/浏览器 profile）的命令，运行前先探测该目录是否可访问（只读 Test-Path/列目录、或看环境 `$env:DSH_*` 权限事实）；未放行就在运行命令时直接带更宽权限（workspace-write / danger-full-access）请求提权、一次到位——不要先以受限权限跑一遍、等 EPERM 报错再回头向用户补授权（「先跑再补」多一次失败、体验差）。→ 对用户只说「这一步需要读写本机登录态目录，需要你授权一下」，不暴露沙箱/权限参数。
